Feature module for the Canvas Quick-Start Guide (PRD v2 — see [`/docs/Canvas Quick-Start Guide PRD.pdf`](../../docs/Canvas%20Quick-Start%20Guide%20PRD.pdf) and [`/docs/Canvas Quick-Start Guide - Feature Roadmap.pdf`](../../docs/Canvas%20Quick-Start%20Guide%20-%20Feature%20Roadmap.pdf)). ## What's built vs. what's scaffolded

- **Day 15 (done):** eligibility check is real and wired into `excalidraw-app/App.tsx`. A browser is "new" only if it has no saved elements, no library items, and no seen-guide flag.
- **Day 16 (done):** opt-in prompt is real (two working actions, not a placeholder, plus a "How to start with Excalidraw" link to `plus.excalidraw.com/how-to-start`); the first hint (`shape-tool`) shows once opted in — with a pulsing highlight on the toolbar's shape buttons — and disappears on its own the moment the user authors a shape themselves, detected via the existing `onChange` scene-change callback; the "end the guide" control actually suppresses further guide state; a user who never interacts with any of it still gets an unblocked, undelayed canvas (P0, re-verified — see `tests/quickstart.test.tsx`) since `onChange` only _observes_ scene changes after Excalidraw has already applied them -- it can't gate or slow drawing. `markGuideSeen()` fires on exposure (first time the prompt is shown to a new user), not on completion -- see the comment on it in `useIsNewCanvasUser.ts` for why that distinction matters.
- **Day 18 (done):** the full four-hint chain is real: `shape-tool` → `labeling` ("Double-click a shape to name this step") → `connecting` ("Draw an arrow to connect two shapes") → `save` ("Your drawing auto-saves in this browser. Use the menu to save a copy."). Each auto-activates once the previous one completes. `labeling` completes on a genuine _bound_ label (`containerId` set), not any text on the canvas; `connecting` completes on an arrow bound at _both_ ends to two _different_ shapes, not a stray or self-looped one. All verified by hand in-browser, not just typechecked. (An earlier note here said double-clicking an _unfilled_ shape doesn't bind the text, which would make the `labeling` copy wrong; it isn't. `handleCanvasDoubleClick` passes `container` to `startTextEditing` whatever the fill -- the fill check only decides whether the caret jumps to the shape's center -- and a live run on a transparent rectangle binds the label and completes the hint.)

  Detection generalized rather than duplicated for the first three hints: `notifySceneChange` doesn't hardcode any of them. It looks up the active hint's completion _predicate_ in `behavior.ts`'s `HINT_COMPLETION` map (`isUserMark` / `isUserLabel` / `isUserConnection`), so a hint with scene-content-based detection just needs a `behavior.ts` entry and a render branch in `QuickstartGuide.tsx` -- the hook itself doesn't change. Two detection rules stay deliberately different, per hint:

  - **Prompt-clear (PRD P1):** a user who never opted in gets the prompt out of the way on their first canvas interaction — any content counts.
  - **Hint completion (PRD P0):** per-hint and mark-aware. `shape-tool` wants any authored mark (not images/imports, per PRD §3); `labeling` wants specifically a bound text label; `connecting` wants an arrow joining two different shapes. Either way, only content the user adds after detection starts counts, and only once.

  Completion tracks which elements _satisfy_ the hint (`HINT_COMPLETION`'s `isSatisfied`), not just which ids are new. Excalidraw inserts an arrow unbound and binds it a moment later under the same id, so a new-id-only check left `connecting` stuck on screen after the user had visibly drawn the connection.

- **Connecting detection (Mofazzal):** `connecting` completes on an arrow bound at both ends to two different shapes _or_ one whose endpoints sit on two different shapes. Bindings alone aren't reliable here: Excalidraw won't bind an arrow to a shape's bound text, so a drag that starts on a label — exactly what the previous hint just taught the user to create — never binds that end. A stray arrow on empty canvas and a self-loop still don't count.

  `save` is architecturally different and deliberately has no `HINT_COMPLETION` entry: clicking Save, Cmd+S, or an Excalidraw+ export don't necessarily change any scene element, so `notifySceneChange` can't see them. It completes via `notifyExplicitSave()` (exported from `useQuickstartGuide.ts`, not returned from the hook) called directly from each of those three gestures' existing `markExplicitlySaved()` call sites (`AppMainMenu.tsx`'s click-capture, `App.tsx`'s Cmd+S/Cmd+Shift+E shortcut handler, and the Excalidraw+ export success callback) -- note that `AppMainMenu.tsx` has to capture on `document` rather than on a wrapper around `<MainMenu>`, because the menu's children are tunneled into the editor's own React tree and their clicks never propagate through the app tree -- reusing `unsavedWork.ts`'s save-state primitives rather than reinventing save detection. Since those call sites live outside `ExcalidrawWrapper`'s component tree, `notifyExplicitSave` reads/writes the guide atoms imperatively via `appJotaiStore` instead of through the hook's `useAtom` setters -- the same pattern `unsavedWork.ts` itself already uses for cross-component state.

- **Help-menu restart (done, Mofazzal):** a "Getting started" button in the Help dialog header (same `HelpDialog__btn` style as Documentation / Blog / GitHub / YouTube, via a new `HelpDialogHeaderTunnel`) reopens the guide after dismiss, including for returning browsers that would otherwise fail eligibility (`guideForcedVisibleAtom`). Existing canvas content is baselined on restart so it doesn't instantly complete the first hint or read as "ignored the prompt."

- **Remote collaborator edits (done, Mofazzal; timing fixed, Lebert):** `Collab.handleRemoteSceneUpdate` records each element's id+version in `remoteScene.ts` before calling `updateScene`, so `App.tsx`'s `onChange` can tell a collaborator's write from the local user's, per element. Remote elements are baselined: they can't complete a hint and can't dismiss the opt-in prompt (P1 is the local user starting to draw on their own). A later local mark still completes the active hint.

  The original version wrapped `updateScene` in a _synchronous_ depth-counted flag, cleared in a `finally` right after that call returned. Verified against a real two-tab collab session (Playwright, two browser contexts, not just unit tests): it never once worked -- `onChange` fires _asynchronously_ relative to `updateScene` (5-10ms later in that trace, not same-tick), so the flag was already back to `false` by the time `onChange` checked it, on every single remote update observed. A collaborator drawing would silently complete hints for everyone else in the room. Fixed by tracking by element id+version instead of a timing-sensitive flag, which survives the async gap regardless of its length and self-expires correctly (a later local edit bumps the element's version, so it stops matching on its own -- no manual cache invalidation needed).

  Checked _per element_, not once for the whole `onChange` batch: `onChange` always reports the full current scene, not a diff, so a single whole-batch boolean would misread every later `onChange` as "remote" forever, the moment any one element had ever been touched by a collaborator and then sat unchanged on the canvas -- breaking local completion for the rest of the session. Covered by `tests/remoteScene.test.ts` (the id+version tracking itself, including surviving a simulated async gap) and `tests/quickstart.test.tsx`'s "a stale remote element sitting unchanged doesn't poison later local completions" regression test.

- **Reload mid-guide (done, Mofazzal):** all the guide state is in-memory atoms, so before this a reload halfway through dropped the user out of the guide entirely — and silently, since their own drawing then failed the eligibility check, so the prompt didn't come back either. `progress.ts` persists the completed hints (only once the user has opted in) and the hook restores them on mount, resuming at the next hint and forcing visibility past eligibility. The drawing on the canvas at that point is baselined, exactly as on a Help restart, so the reload doesn't hand the user the step they were in the middle of. Nothing is stored for a user who never opted in (P0), and the entry is removed when the chain finishes or the guide is ended.

- **Narrow widths (done, Mofazzal):** the prompt is a single flex row, which at phone widths pushed its buttons off both edges of the screen. It now wraps, caps at `calc(100vw - 24px)`, and lets the copy shrink before the buttons do (`white-space: nowrap; flex: none`), so the actions stay reachable at 375px.

- **Not built yet:** analytics (Day 20) has been cut from scope; `types.ts`'s `QuickstartEventName`/`QuickstartEvent` types are unused scaffolding, left in place but not wired to anything.

## Conventions

- Shared state uses Jotai atoms (`../app-jotai`), matching the rest of `excalidraw-app` (see `collabAPIAtom`, `shareDialogStateAtom`) — not React Context. Anything reading/writing the atoms outside React must go through `appJotaiStore`, the same store `<Provider>` mounts in `App.tsx`.
- `QuickstartEvent` must never carry drawing text, images, or scene contents (Day 20 P0, PRD §3). Metadata only.
- Eligibility stays on-device (`localStorage` + IndexedDB), not account-based — a returning guest who's never signed up must still read as not-new (PRD §1b).
